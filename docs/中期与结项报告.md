# Satori 中期与结项报告：架构与数据流分析

## 1. 设计理念：为何没有传统 ER 图与 SQL？

在传统的管理信息系统（MIS）中，系统设计的核心通常是**实体关系（ER）**和**关系型数据库（SQL）**。传统系统侧重于事务处理（CRUD）、严格的数据一致性以及多表之间的复杂关联（如外键、一对多、多对多映射）。

**Satori 与传统信息管理系统截然不同。** Satori 是一个**语义检索系统**，其核心目标是将“白话”与“黑话/网络梗”映射到同一个检索空间中。因此，它的底层数据并非高度规范化的关系型数据，而是**文档（Document）**和**高维向量（Vector Embeddings）**。

在 Satori 中：
- **没有 SQL**：我们不使用 MySQL 或 PostgreSQL 等关系型数据库，因为检索请求不是结构化的条件过滤（如 `WHERE age > 18`），而是模糊的自然语言匹配。
- **没有 ER 图**：数据形态是扁平化、自包含的“数据卡片（JSON Cards）”，不需要跨表 Join 操作。

为了替代传统的 ER 图，本报告将通过**系统架构**、**数据结构（卡片模型）**和**数据流转原理**来详细阐述系统的运作方式。

---

## 2. 系统整体架构

Satori 采用前后端分离的架构，后端基于 Rust 构建了高性能的检索引擎。系统主要由以下几个核心模块构成：

1. **前端交互层 (Frontend)**
   - 技术栈：React + TypeScript + Vite
   - 职责：提供极简的用户搜索界面，接收用户输入的白话或黑话，渲染搜索结果（包含词条、白话解释、例句、标签等）。

2. **API 网关层 (`crates/api`)**
   - 技术栈：Rust + Axum + Tokio
   - 职责：暴露 HTTP RESTful API（如 `/api/search` 和 `/api/health`）。负责接收前端请求，将其路由到具体的检索后端，并将检索结果序列化为 JSON 返回。

3. **核心检索引擎 (`crates/core`)**
   - 职责：封装搜索逻辑和排序算法。
   - **双引擎支持**：
     - **内存关键词检索**：项目初期和兜底方案。在应用启动时，将 JSON 数据卡片加载至内存并构建倒排索引或直接匹配规则。根据预设的权重（如 `term` > `queries` > `包含匹配` > `双字重叠`）对结果进行打分排序。
     - **向量语义检索**：集成 LanceDB。将用户的自然语言 query 通过 Embedding 模型（如 `paraphrase-multilingual-MiniLM-L12-v2`）转化为向量，在多维空间中计算余弦相似度（或 L2 距离），从而实现“模糊语义”的精准召回。

4. **数据管道与索引构建 (`crates/indexer`)**
   - 职责：作为离线数据处理中枢，负责语料的清洗、校验、导入及索引构建。
   - 支持从外部语料（如 `mcsrainbow/chinese-internet-jargon`）提取数据。
   - 负责将原始 JSON 数据导出为 LanceDB 需要的向量数据库格式。
   - 包含回归测试框架（基于 `tests/fixtures/regression.json`）评估搜索准确度。

## 3. 数据模型：JSON 数据卡片

替代传统 ER 图的是 Satori 的核心数据单元——**数据卡片**。每一条黑话或梗都是一个独立、闭环的 JSON 对象。

```json
{
  "id": "jargon_lar_tong_dui_qi",
  "term": "拉通对齐",
  "plain": "大家先统一想法",
  "explanation": "让相关的人先把目标、分工和时间说清楚。",
  "examples": [
    "这个需求先拉通对齐一下。"
  ],
  "queries": [
    "大家先统一想法",
    "先把要做的事情说清楚"
  ],
  "tags": ["职场", "会议", "协作"],
  "source": "manual",
  "verified": true
}
```

**字段释义（数据字典）：**
- `id`: 唯一标识符。
- `term`: 目标黑话或网络梗（检索核心目标）。
- `plain`: 对应的标准大白话/人话。
- `explanation`: 详细解释，用于辅助理解。
- `examples`: 实际应用场景的例句数组。
- `queries`: 常见的用户提问方式扩展，用于增强检索命中率。
- `tags`: 领域标签（如“职场”、“互联网”）。
- `source` & `verified`: 数据来源与人工校验状态。

这种反范式（Denormalized）的设计极其适合检索引擎，所有参与计算相似度或匹配的文本内容（`term`, `plain`, `explanation`, `examples`, `queries`）都聚集在一起，检索时一次读取，无需任何 Join 操作。

## 4. 数据流与工作原理

整个系统的数据流转分为**离线数据处理流**和**在线检索流**。

### 4.1 离线数据处理流（Data Pipeline）

这是数据从“原始语料”变成“可检索索引”的过程。

1. **获取原始语料 (Ingestion)**:
   - `satori-indexer` 抓取外部 GitHub 仓库或读取本地临时文件（放入 `data/raw`）。
2. **清洗与规范化 (Processing)**:
   - 提取可用字段，映射到 Satori 的 JSON 卡片结构。
   - 存入 `data/processed/cards.json`。此时数据已可被“内存关键词检索”使用。
3. **向量化与建库 (Embedding & Indexing)**:
   - 运行 `export-index-docs` 将卡片扁平化为适合向量化的文本（如合并 term 和 queries）。
   - 运行 `build-lancedb-index`，调用 Embedding 模型，将文本转化为高维浮点数向量。
   - 将向量数据和 payload 写入本地 LanceDB（存放在 `data/processed/lancedb`）。

### 4.2 在线检索流（Search Data Flow）

这是用户在前端输入一段文字后，系统内部的流转过程。

1. **请求发起**:
   - 用户在前端输入：“大家先统一想法”。前端发送 HTTP GET 到 `/api/search?q=大家先统一想法`。
2. **路由解析**:
   - Axum 接收到请求，提取 query 参数，并将其传递给 `crates/core` 的搜索接口。
3. **检索引擎路由**:
   - **若配置了向量库 (LanceDB)**：系统将 `q` 送入 Embedding 模型生成查询向量，前往 LanceDB 表进行 KNN（K近邻）搜索，返回最相似的卡片 ID 及分数。
   - **若使用默认内存检索**：系统遍历内存中的倒排索引和匹配规则，通过完全匹配、子串包含、双字重叠等规则，计算出每张卡片的相关度打分（Score）。
4. **排序与组装**:
   - 将召回的结果按照 Score 降序排列。
   - 拼装完整的 JSON Card 结构。
5. **返回与渲染**:
   - 后端返回 JSON 列表。
   - 前端接收到结果，渲染黑话词条及其例句，完成一次搜索闭环。

---

## 5. 结语

Satori 项目脱离了传统关系型数据库的束缚，拥抱了适合自然语言处理的**文档+向量检索**架构。通过清晰的前后端职责划分、离在线解耦的数据管道，以及面向检索优化的扁平化数据卡片设计，成功实现了一个高效、精准且易于扩展的“白话<=>黑话”双向语义搜索引擎。
